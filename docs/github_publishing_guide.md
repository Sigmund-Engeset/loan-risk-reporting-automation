# Publishing this project on GitHub

A recruiter spends about a minute on a GitHub profile. The goal is that in that minute they see: what you built, why it mattered, and that the code is clean. This guide covers the repository, the profile around it, and the checks to do before anything goes public.

---

## 1. Portfolio structure: one repo per project + a profile README

```
github.com/Sigmund-Engeset                         ← profile page (landing page for recruiters)
├── Sigmund-Engeset/Sigmund-Engeset                ← special repo: its README is shown on your profile
├── loan-risk-reporting-automation                 ← this project
├── inc5000-power-bi-dashboard                     ← other projects, one repo each
└── ...
```

- **One repo per project.** Each gets its own README, can be pinned, and can be linked from a CV or LinkedIn post. A single "portfolio" repo with many folders buries your best work.
- **Pin your 4–6 best repos** on your profile (Profile → *Customize your pins*).
- **Profile README** (section 6) is your landing page.

## 2. Before you push: the confidentiality and secrets check

This is the step that matters most for someone coming from a bank.

**Confidentiality**
- [ ] No real data, not even "anonymised" extracts. Everything here is generated by `scripts/generate_mock_data.py`.
- [ ] No internal table names, column names, system names, file paths or e-mail templates copied from work. The names in this repo are generic, keep it that way if you edit them.
- [ ] Employer described generically ("a major Nordic bank"). Naming your employer on your CV is normal, but implying that the repo contains their process documentation is not. Check your employment contract and code-of-conduct rules on side projects if you are unsure.

**Secrets**
- [ ] `.env` exists locally but is listed in `.gitignore`.
- [ ] Private key (`rsa_key.p8`) is stored **outside** the repo folder.
- [ ] Run `git status` before the first commit and read every file name it lists.

If a secret ever gets committed: deleting it in a later commit is **not enough**, it remains in the history. Rotate it (generate a new key / password) immediately, then clean the history or recreate the repo.

## 3. One-time Git setup

Use GitHub's private no-reply address for commits so your personal e-mail is not published in the commit history. Find it under **GitHub → Settings → Emails** (format `12345678+Sigmund-Engeset@users.noreply.github.com`), and tick *Keep my email addresses private*.

```bash
git config --global user.name  "Sigmund Engeset"
git config --global user.email "12345678+Sigmund-Engeset@users.noreply.github.com"
git config --global init.defaultBranch main
```

## 4. Create the repo and push

### Option A: GitHub CLI (fastest)

Install from https://cli.github.com, then run `gh auth login` once.

```bash
cd loan-risk-reporting-automation
git init
git add .
git status                      # read the list. No .env, no output/, no keys?
git commit -m "Loan risk reporting automation: Snowflake to Excel reports and e-mail alerts"
gh repo create loan-risk-reporting-automation --public --source=. --push \
  --description "Automated loan risk reporting: Snowflake → pandas → country/branch Excel reports + relationship-manager e-mail alerts"
```

### Option B: Website + command line

1. GitHub → **New repository** → name `loan-risk-reporting-automation`, **Public**, and do **not** add a README, .gitignore or license (they already exist here).
2. Then:

```bash
cd loan-risk-reporting-automation
git init
git add .
git status
git commit -m "Loan risk reporting automation: Snowflake to Excel reports and e-mail alerts"
git remote add origin https://github.com/Sigmund-Engeset/loan-risk-reporting-automation.git
git push -u origin main
```

When asked for a password, use a **Personal Access Token** (Settings → Developer settings → Personal access tokens), not your GitHub password. GitHub Desktop is a fine alternative if you prefer a UI.

### Commit history

One clean initial commit is fine. From here on, commit in small logical steps with messages that say *what and why*:

```
Add phone number standardisation to E.164
Fail on unmapped country values instead of dropping rows
Add pytest tests for cleaning functions
```

A recruiter-facing repo with a history of `update`, `fix`, `asdf` looks careless. Don't fabricate a fake history either; just be deliberate from now on.

## 5. Polish the repo page (5 minutes, high impact)

On the repo page, click the ⚙ next to **About**:

- **Description:** one line, outcome-first (the one used in the `gh` command above).
- **Topics:** `snowflake` `python` `pandas` `sql` `data-engineering` `analytics-engineering` `automation` `excel` `jupyter-notebook` `banking` — topics make the repo searchable.
- **Website:** your LinkedIn URL.
- Untick *Releases*, *Packages*, *Deployments* if unused, to keep the sidebar clean.

Then **pin** the repo on your profile.

### Check that the notebook renders

Open the `.ipynb` on GitHub. It should display with all outputs and the chart. GitHub's notebook renderer occasionally fails on larger notebooks ("Unable to render code block"). If so, link to nbviewer instead, which always works for public repos:

```
https://nbviewer.org/github/Sigmund-Engeset/loan-risk-reporting-automation/blob/main/notebooks/loan_risk_reporting_pipeline.ipynb
```

**Keep the outputs in the notebook.** A recruiter will not run your code; they read the outputs. Re-run the whole notebook top to bottom (**Kernel → Restart Kernel and Run All Cells**) before each commit so cell numbers are in order 1, 2, 3… Out-of-order numbers look like untested code.

## 7. Promote it

- **LinkedIn post:** the problem in one sentence, the before/after, one image (`docs/images/branch_report_preview.png` or a screenshot of the notebook), and the repo link. Posts with a concrete "I replaced X manual steps with one run" story outperform tool lists.
- **CV:** add the repo link next to the matching bullet under your bank role.
- **Interviews:** be ready to walk through the design decisions in the README (why Python over VBA, why `validate="one_to_one"`, why drafts and not auto-send). That is where this project earns its keep.

## 8. Updating later

```bash
git add -A
git commit -m "Describe the change"
git push
```

Adding new mock data? Change `SEED` or `N_CUSTOMERS` in `scripts/generate_mock_data.py`, regenerate, reload into Snowflake, and re-run the notebook so outputs and README numbers stay consistent.
